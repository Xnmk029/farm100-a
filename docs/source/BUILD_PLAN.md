AI 算法农场 Benchmark 客户端：基础构建计划

本计划基于《编程农场》的讨论，目标是把模型生成的算法代码转换为可观察、可回放、可比较的游戏运行过程，服务于 AI 测评与内容制作。当前项目目录为空，本轮只制定计划。

以下技术与规则是首版建议。暂按 Windows 桌面客户端、本地运行、二维俯视农场、单无人机规划；目录结构和接口保留后续扩展空间。

1. 产品目标与首版使用流程

首版完成一条完整流程：选择关卡和测试种子 → 导入或粘贴模型代码 → 执行程序 → 观察农场行为与运行指标 → 回放关键过程 → 对比不同解法 → 导出结果。

用户应能回答三个问题：这个解法做了什么、为什么成功或失败、相比另一个解法节省了哪些操作。

界面安排：

| 区域 | 首版职责 |
| --- | --- |
| 任务设置 | 查看规则，选择地图规模、种子和操作预算 |
| 代码区 | 导入、编辑和保存参赛代码，标记模型名称及尝试编号 |
| 农场画布 | 展示无人机、作物数值、移动轨迹、交换动作和完成状态 |
| 运行控制 | 启动、中止；控制回放的暂停、单步、倍率和进度 |
| 指标与日志 | 展示操作统计、剩余预算、错误和通关结果 |
| 对比视图 | 用相同关卡配置对齐两次运行，比较过程和指标 |

运行状态至少区分：准备中、执行中、完成、失败、超出预算、用户中止。回放状态与程序执行状态分别管理。

2. 首个关卡：作物排序与整田收获

建议制作一个受仙人掌玩法启发的独立关卡，先验证排序行为是否清楚、不同算法是否具有可见差异。

| 项目 | 建议规则 |
| --- | --- |
| 场景 | 从 4×4 调试地图起步，以 8×8 作为首个标准演示规模 |
| 输入 | 固定种子生成的整数网格；数值映射为作物高度，并可显示数字 |
| 角色 | 一台无人机，起点固定，四向移动，边界不环绕 |
| 目标 | 每行从左到右、每列从上到下均非递减，然后成功执行整田收获 |
| 观察能力 | 读取地图尺寸、自身坐标、脚下或相邻田块的数值 |
| 操作能力 | 移动、测量、与相邻田块交换、尝试收获 |
| 验证 | 引擎检查完整网格的行列约束，并确认作物数值集合保持不变 |
| 难度来源 | 地图规模、数值分布、初始有序程度和操作预算 |

首版 API 建议为 `get_size()`、`get_position()`、`move(direction)`、`measure(direction?)`、`swap(direction)`、`harvest()`。方向约定、返回值、越界行为、错误行为和操作成本在实现前写入版本化规则。

先提供少量便于解释的示例局面，再加入固定种子的测试集。制作一个简单参考解法和一个减少操作的改进解法，用于验证关卡、评分和画面能否呈现差异。

3. 技术架构

推荐使用 Electron + React + TypeScript + PixiJS。桌面壳负责本地文件和窗口，React 负责编辑与测评面板，PixiJS 负责二维农场画面。这组技术适合同时容纳代码编辑、游戏过程和结果比较。

| 模块 | 技术建议 | 职责 |
| --- | --- | --- |
| 桌面应用 | Electron | 窗口、文件导入导出、启动运行器、打包 |
| 操作界面 | React、TypeScript、Vite | 任务配置、代码编辑、结果列表与对比 |
| 农场渲染 | PixiJS | 将状态快照和事件转换为画面与动作反馈 |
| 模拟核心 | 独立 TypeScript 模块 | 地图状态、规则、动作校验、计费与通关判断 |
| 脚本运行器 | 独立 utility process；QuickJS/WASM 方案待原型验证 | 执行参赛代码，通过受控 API 调用模拟核心 |
| 记录与回放 | 版本化 JSON、事件序列、周期快照 | 保存配置、代码、执行过程、指标与结果 |

数据流为：界面提交代码和配置 → 运行器执行脚本 → 模拟核心处理动作 → 产生事件及结果 → 界面渲染、记录和回放。

模拟核心独立于 Electron 和 PixiJS，应能在无界面环境中执行同一个关卡。运行器与界面之间使用版本化消息协议；界面接收快照与事件，所有影响计分的状态变化由模拟核心处理。

首版脚本语言建议使用 JavaScript，以便先验证 QuickJS/WASM 的受限运行能力。后续需要 Python 时增加语言适配器，复用关卡 API、事件协议和评分规则。这个选择需要在运行器原型阶段验证后冻结。

4. 执行边界、计分与复现

参赛代码运行在独立进程中的受限解释器内，只注入关卡 API。宿主文件、网络和系统命令能力不向脚本开放。配置解释器内存上限、执行中断、游戏操作预算、日志及事件数量上限，并由宿主提供超时终止兜底。

Electron 界面启用上下文隔离和渲染进程沙箱，关闭 Node 集成；本地文件操作通过范围明确的 preload 接口完成。正式接入参赛代码前，验证死循环、超量分配和日志洪泛能够被中止，且界面保持响应。

每次运行记录：

| 记录类别 | 内容 |
| --- | --- |
| 输入 | 关卡及规则版本、引擎和运行器版本、种子、初始地图、预算配置 |
| 解法 | 原始代码、代码哈希、模型标签、尝试编号 |
| 结果 | 是否通关、终止原因、最终状态、移动/测量/交换等分类计数 |
| 过程 | 有序事件、逻辑步序号、周期快照 |

成功与否是第一层评价，成功解法再比较操作成本。首版显示分类操作计数和总逻辑成本；成本表随规则版本固定，在参考解法和改进解法上验证后冻结。预算耗尽或异常终止的运行保留失败原因与已完成进度。

模拟器采用固定种子的伪随机序列。实际机器耗时作为辅助记录；播放倍率不参与计分。模型生成和修复代码所需的时间、Token 与尝试次数作为独立维度，首版允许手工填写来源明确的记录。

回放直接使用已保存的事件及快照，拖动进度时从最近快照恢复。程序执行采用分批事件传输与背压，限制单次运行和消息队列的体积。对比默认按逻辑成本对齐，两份代码必须使用一致的关卡配置。

5. 分阶段构建顺序

| 阶段 | 构建内容 | 验收条件 |
| --- | --- | --- |
| P0：规则与运行器验证 | 规则 v0.1、API 文档、事件格式、最小脚本执行原型 | 参考程序能够调用 API；死循环和内存超限能够终止；确定脚本语言及解释器 |
| P1：客户端骨架 | Electron、React、PixiJS 集成；任务面板；导入保存；基础网格 | Windows 本地开发环境能启动，可保存配置和代码并重新打开 |
| P2：模拟核心 | 地图生成、单无人机、移动测量交换、收获验证、计数和预算 | 无界面参考解法可通关；相同代码与配置重复运行得到相同事件及结果 |
| P3：运行与画面连接 | 运行器驱动引擎；将真实事件接入画布和日志；处理中止与错误 | 用户代码可完成整田排序收获；错误、中止、超限有明确反馈，界面可继续使用 |
| P4：回放与解法对比 | 事件存储、快照、单步/倍速/跳转、双视图和指标比较 | 保存后重新打开可完整回放；跳转与顺序播放状态一致；倍速不改变计分 |
| P5：可分发首版 | 固定测试集、批量运行、参考解法、演示案例、结果导出、安装包 | 在没有开发环境的 Windows 机器上可安装运行、复现案例并导出结果 |

优先完成 P0，确认规则和运行器可行，再推进 P1—P3 的完整流程。P3 完成后即可判断核心体验；P4—P5 将其整理为可用于测评的客户端。

必要验证集中在规则正确性、确定性、执行限额、回放一致性和 Windows 打包后的实际运行。界面调整通过实际运行与视觉检查验证。

6. 建议目录结构

```text
benchmark/
  apps/desktop/          # Electron 主进程、preload、React 界面
  packages/protocol/     # 运行请求、事件、快照、结果的数据格式
  packages/simulation/   # 无界面的确定性模拟核心
  packages/runner/       # 受限脚本执行和 API 桥接
  packages/farm-view/    # PixiJS 农场渲染与回放呈现
  scenarios/             # 关卡定义、成本表、固定种子测试集
  examples/              # 参考解法与演示解法
  docs/                  # 规则、API、计分、使用说明
  BUILD_PLAN.md
```

运行记录存入客户端的用户数据目录，导出时由用户选择目标位置。首版使用文件存储即可；记录格式携带版本号，便于后续迁移。

7. 后续迭代方向

在首版验证完成后，依次考虑迷宫寻路、补种任务等新关卡，多无人机调度，模型 API 自动调用及修复轮次记录，以及适合内容制作的字幕、镜头控制和视频导出。macOS/Linux 分发与 Python 运行器根据实际需求推进。

下一步实施任务是 P0：确定排序规则与操作成本草案，定义运行消息格式，并用最小代码验证受限脚本运行和强制中止能力。
