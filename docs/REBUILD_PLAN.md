## 1. 产品方向与范围

从零重建一个 Windows 本地 AI 算法农场 Benchmark 客户端。首版实现：选择关卡与种子 → 导入或编辑 JavaScript 解法 → 执行 → 观察真实动作和指标 → 保存 → 回放 → 同配置双解法对比 → 批量测试与导出。

首个关卡是“作物二维排序与整田收获”：玩家编程控制单无人机，通过测量、移动和相邻交换，让每行从左到右、每列从上到下非递减，然后执行收获。画面采用二维俯视农场。

本次“完全重建”包含客户端、模拟核心、运行器、协议、记录格式、回放、计分和验证体系。旧 Python 模拟器、旧评分函数、Three.js 回放和旧数据格式均不进入新实现。旧内容归档供追溯；新测试可以采用本次审计暴露的问题作为回归场景。

首版边界：

- Windows x64 桌面应用；本地离线运行，安装后核心能力不依赖开发环境或联网服务。
- 单关卡，4×4 调试、8×8 标准演示、16×16 压力测试。
- JavaScript 为首版参赛语言，采用受限解释器；是否使用 QuickJS/WASM 在 P0 验证后冻结。
- 手工导入模型代码；模型生成耗时、Token、尝试次数可以手填并标明来源，不自动推断。
- P5 必须交付批量测试、双解法对比、可重开的运行包和 Windows 安装包。
- 迷宫、补种、多无人机、Python、模型 API 自动调用、视频导出、3D 与跨平台分发进入后续版本。

“FARM100”沿用项目名称。首版评价以通关和真实操作成本为核心，不继承旧版 55+30+10+5 的百分制。

## 3. 架构决策

采用 Electron + React + TypeScript + Vite + PixiJS，代码编辑采用 Monaco Editor。首版不引入服务端、数据库、通用插件框架或多语言抽象引擎。

```text
FARM100/
  apps/desktop/
    src/main/          # 生命周期、文件 IO、运行器管理、导入导出
    src/preload/       # 范围明确的类型化 IPC
    src/renderer/      # React 工作台、编辑器、结果与对比界面
  packages/protocol/   # 类型、运行时校验、版本、规范化与哈希
  packages/simulation/# 纯 TS 场景、状态、规则、计费、通关判断
  packages/runner/    # QuickJS 适配、API 桥接、中断、限额
  packages/recording/ # 事件归约、快照索引、运行包读写与验证
  packages/farm-view/# PixiJS 绘制、动作动画、可视化标记
  scenarios/sort-field-v1/
    fixtures/         # 可解释的固定局面
    suites/           # 版本化种子与配置清单
  examples/           # 参考解、改进解、失败与超限示例
  tests/              # 跨模块正确性、确定性、运行边界与打包检查
  docs/               # 规则、API、协议、测评、使用、验收证据
  package.json
  pnpm-workspace.yaml
  pnpm-lock.yaml
```

职责分隔：

- Electron 主进程负责保存文件、启动/终止 utility process 和消息转发。
- 每次运行建立新的受限 VM；模拟核心与 VM 桥接位于 utility process 内，核心执行同步 API，避免每一步跨进程往返。
- VM 仅获得数据副本及指定 API，不获得引擎对象、宿主函数内部引用或任意 IPC。
- React/PixiJS 只消费可信运行器事件和状态，不生成成绩，不直接修改计分世界。
- 记录与回放使用同一份状态变更事件，动画是视觉插值，不影响逻辑世界。
- 模拟核心可脱离桌面在命令行批量运行，为 CI 和回归测试提供入口。

## 4. 首关规则 v0.1 草案

### 4.1 状态和目标

- 坐标原点左上角；x 向右、y 向下。North=(0,-1)，South=(0,1)，East=(1,0)，West=(-1,0)。边界不环绕。
- 正方形网格，格值为 0～9 的整数，允许重复。起点固定 (0,0)。地图生成使用固定算法、固定版本的整数 PRNG。
- 初始作物均成熟。首关不包含生长、货币、种植成本或科技解锁，以便明确测量排序行为。
- 唯一通关条件：所有行列非递减、当前数值多重集合等于初始集合，并成功调用 harvest()。
- 引擎必须验证完整网格，不能根据局部画面、排序标记或参赛代码的布尔返回值判通关。
- 排好序后未收获、脚本正常结束但未完成目标，均不算通关。
- 成功收获立即结束运行，保留收获前最终网格作为验收证据；清田只是结束动画。

### 4.2 API 与成本草案

| API | 返回和语义 | 逻辑成本 |
| --- | --- | ---: |
| get_size() | 边长整数 N | 1 |
| get_position() | 新对象 {x,y} | 1 |
| move(direction) | 相邻合法位置返回 true；越界返回 false，位置不变 | 1 |
| measure(direction?) | 不传方向读脚下；传方向读相邻；越界返回 null | 1 |
| swap(direction) | 合法相邻位置交换值并返回 true；越界返回 false | 3 |
| harvest() | 引擎全局验证；未满足返回 false，满足则记录成功并终止 | 1 |

类型错误、非法方向或参数数量错误产生 api_error 并终止，不改变网格。合法调用即使越界或收获失败也按表收费，避免无限免费探测。最终 API 文档须明确无参数、undefined、null、NaN 等边界输入。

每次 API 调用先校验参数，再检查剩余预算是否覆盖完整费用；预算不足时立即结束，动作不执行、不部分扣费，已用成本永不超过上限。刚好用完预算时若本次 harvest 已成功，结果为成功；否则在继续调用时报告超出预算，脚本自行结束则记录未完成目标。

同步执行顺序固定为：校验 → 预算预检 → 扣费 → 操作/结果 → 分类计数 → 唯一事件。开始/结束等元事件不携带额外收益或动作成本。

首版允许 Array.sort() 等标准语言能力。关卡主要考核受限观察与移动交换成本；内部计算不计入世界操作成本，实际计算耗时另记。不能将这个指标描述为完整 CPU 算法复杂度。

预算先按 4×4/8×8/16×16 分别配置 2,000/20,000/200,000 的草案值，P0/P2 用实际解法测定后冻结。成本表改变必须升级规则版本。

### 4.3 成绩呈现

- 单次运行先显示是否通关；成功运行再比较总逻辑成本，并展开 move/measure/swap/harvest/查询的分类次数。
- 失败显示明确原因、已用成本及相邻行列约束违反数。违反数仅为诊断，不代表可替代通关的分数。
- 测试集优先比较通过率；通过同一组案例的解法再比较共同案例成本。对不同成功子集，不直接比较总成本来宣称优劣。
- 相同成本视为并列，不使用动画时间或机器快慢破坏并列。
- 首版不输出未经校准的百分制、不以自身作为标杆，也不将手填模型名称当作真实模型调用证明。

## 5. 执行边界与状态机

P0 首选验证 QuickJS/WASM 在 Electron utility process 中的运行。必须实证 API 桥接、同步执行、解释器中断、内存限制、WASM 资源随打包定位和进程回收，之后才能固定依赖版本。

边界要求：

- 不注入文件、网络、系统命令、Node、Electron、宿主 require/import；禁止动态加载外部模块。
- Date 和未固定的 Math.random 不暴露给参赛代码；首版无宿主异步 IO 或脚本定时器。
- 标准语言内建可以使用，只有 API 能影响世界。
- VM 内存上限初始草案 128 MiB；代码文件上限 1 MiB；控制台输出上限 256 KiB；运行记录上限 64 MiB。日志到上限后截断并标记，计分事件不得静默丢弃。
- API 调用数与总操作成本均有上限，循环查询同样消耗预算。
- VM 中断和主进程超时终止并存；墙钟超时草案 30 秒。P0 明确解释器执行配额可支持到什么粒度，不把中断轮询次数冒称精确指令计数。
- 用户中止由主进程处理；即使 VM 不配合，也能结束 utility process，目标是在点击后 2 秒内得到终态并可再次运行。
- 队列使用有序分批传输和确认背压；上限触发时终止并明确记录，不能用少录事件来伪装正常完成。
- Electron 使用 contextIsolation、sandbox，关闭 nodeIntegration；preload 仅暴露选文件、保存、启动、中止等明确操作；严格限制导航与外部资源加载。参赛代码及模型标签始终按文本显示。

执行状态：idle → preparing → running → succeeded / failed / budget_exceeded / cancelled。失败细分 syntax_error、api_error、runtime_error、memory_limit、wall_timeout、recording_limit、runner_crash、incomplete 等原因。

回放状态独立为 unloaded / paused / playing / ended。暂停画面不等于暂停程序；中止程序不等于暂停回放。新一轮 runId 隔离旧消息，快速连续启动/中止不能污染新成绩。

正常完成与逻辑预算终止的运行要求确定性复现。墙钟超时、进程崩溃等终止点可能受机器影响，应标明其性质，不承诺在不同机器产生相同终止事件。

## 6. 消息、存储、回放与对比

消息携带 protocolVersion、runId、sequence；包含 start、ready、eventBatch、ack、cancel、result、error。宿主做运行时 schema 校验，处理重复、缺失、乱序、旧运行消息和崩溃。

每条动作事件记录序号、累计成本、动作参数、返回结果、状态变化及分类计数增量。只在模拟核心统一发出一次；不能在 API 包装层重复计分。初始状态、阶段快照和终态须包含完整网格与位置。

运行包内容：manifest、config、source.js、initial-state、events、snapshots、result，可额外包含明确标记来源的 generation-metrics。配置记录关卡/规则/成本表/引擎/运行器/PRNG 版本、种子、初始地图和预算；代码存原文和 SHA-256。

成绩计算只读取可信原始结果与事件，不从画面重算。配置指纹使用规范化序列化。重复运行比对逻辑事件与最终状态哈希，排除 runId、时间戳和机器耗时。哈希用于一致性与损坏检测，不构成来源认证或防伪签名。

记录存入 Electron userData 下的 FARM100 目录，先写临时记录再完成封存。执行中断保留已确认的事件前缀并标记记录不完整。导入运行包时验证版本、大小、路径和 schema，禁止压缩包路径越界；导入代码默认不自动执行。

快照初始每 256 个动作事件一次，另保存初始与最终状态。跳转从最近快照按事件归约到目标位置；对比与回放均采用完整事件，不拿稀疏快照连线冒充真实路径。

对比只允许同配置指纹的成绩参与正式并排比较；同时核对初始地图。默认按累计逻辑成本对齐，使用“不超过当前成本的最后一个完整事件状态”，不在 swap 的中途生成逻辑状态。可以切换各自事件单步，但界面明确对齐方式。较早完成的一侧停留在终态。

首版不承诺逐源码行准确跟踪。界面先突出真实 API 动作、坐标和数值变化；源码位置或堆栈只在解释器确实提供可靠数据时展示，禁止根据调用次数猜测执行行。

## 7. 画面与使用体验

以农场为中心，采用清晰的二维俯视画面、可读的整数和作物高度，保持排序关系容易观察。首次启动直接载入一个 4×4 示例，提供“载入参考解并运行”，同时明确其人工参考来源。

工作台布局：顶部选择场景、种子、预算与模型标签；左侧任务说明和案例；中间农场；右侧 Monaco 代码区；底部动作时间线、播放控制和指标。对比模式使用两块同尺度农场，共享成本进度。

画面必须表达：当前位置与朝向、测量目标和值、相邻交换的两格、已满足/违反的约束、收获成功与失败、路径。颜色辅以图标和数字。长轨迹提供最近若干步/全部/隐藏选择，避免密集交叉线遮蔽作物。

视觉迭代顺序为基础网格与数字 → 动作反馈 → 农场素材与层次 → 排版和对比阅读。所有素材随安装包离线提供并登记许可。先保留无需外部素材的确定性调试视图，素材加载失败不阻断规则或回放。

验证重点覆盖 1280×720、1920×1080 和 Windows 高 DPI。错误时保留代码，显示具体原因，修正后可以再次运行。程序运行、播放和正在录制的状态不能混用标签。

## 9. 必须覆盖的验证

### 规则与确定性

- 全相等、已全有序、完全逆序、重复值、单处错序、行有序列无序、列有序行无序、蛇形有序但不满足二维约束。
- 独立验证器检查行列关系和多重集合，不能只调用被测引擎内部同一个判断函数完成所有测试。
- 对小规模局面穷举/属性验证相邻交换不丢值，边界失败不改变地图；不同种子含可到达、可完成的题目。
- 简单参考解采用“逐行排序，再逐列排序”的相邻交换实现；用性质测试确认第二阶段保持行约束。
- 改进解从减少重复测量、减少无效移动和减少无效比较入手，在固定案例上证明成本降低，不宣称全局最优或每个种子都优于参考解。
- 同代码、同初始地图、同版本和预算重复运行 10 次，比较完整逻辑事件及结果；墙钟终止案例单独评估。

### 运行边界与记录

- 预算为 0、费用刚好够、swap 仅差 1、末动作收获成功；中止请求落在准备、执行和结束边界。
- while(true)、深递归、大数组、异常、非法 API、日志洪泛、连续运行、旧 runId 消息、utility process 崩溃。
- 输入代码尝试访问宿主能力，确认无文件、网络、Electron 或 Node 引用泄漏。
- UI 慢消费、磁盘写入失败和记录上限均明确失败，不丢计分事件后假报完整记录。
- 单步计数和事件累计成本等于结果；一次动作只记录一次。禁止重现旧版宝藏双计分问题。

### 回放与发布

- 每次运行抽取至少 100 个跳转位置，与从初始状态顺序重放的结果比对。
- 完整保存与加载保留网格、位置、计数和终态，禁止旧版“5×5 读成 1×1”问题。
- UI 视觉检查与真实操作验证，截图不能替代暂停、中止、重开、比较、导出的功能验收。
- 使用打包后程序检查 WASM、字体、素材和编辑器 worker 路径，离线复现示例。
- 干净 Windows 验收必须有实际环境证据；若仅在本机测试，P5 对应项保持未验收，不宣称完成。

## 10. 最终交付与当前下一步

完成版本应包含：新源码与锁文件、规则/API/协议说明、测试集和参考解、Windows 安装包、至少一对同配置解法运行包、可比较指标导出、验收记录和已知限制。

这份计划不以重建旧科技树为首版目标，而以 BUILD_PLAN 描述的完整测评客户端为验收对象。后续游戏扩展必须继续复用可信模拟核心、版本化记录与回放机制。

当前仅规划完成。进入实施后，从 R0 归档和 P0 规则/运行器验证开始；首先交付可实测的规则与运行边界证据，再推进客户端生产。
