# FARM100 产品目标：具有完整游戏深度的可编程农场

原始目标设计日期：2026-09-07。当前已转入实施，阶段进展见 [流式与分页](STREAM_IMPLEMENTATION.md)、[历史与恢复](HISTORY_IMPLEMENTATION.md) 和 [多机实施记录](FLEET_IMPLEMENTATION.md)。下文保留原始目标、当时基线及验收门槛，整体目标尚未达成。

## 1. 总目标

将 FARM100 从单关算法测评工具，建设为在观赏性、自动化经营深度和编程挑战层次上，达到《编程农场》（The Farmer Was Replaced）同等级体验的原创农场游戏，同时保留可信的 AI 算法测评、回放和对比能力。

完成后的体验应是：代码驱动无人机耕作，田地持续生长和变化；产出支持新的种植与研究，研究解锁更复杂的作物规则和调度能力；玩家从控制一块田，逐步发展到编排多个生产区域与多台无人机。观看者能直接看到策略造成的效率差异、失败和恢复。

观赏性与系统复杂度分别验收，任一未达标都不能宣布达到目标。漂亮的静态截图、堆积功能数量、扩大网格或延长等待时间，都不能单独证明目标达成。

## 2. 对标边界与当前差距

本目标中的原版指 The Farmer Was Replaced。本轮没有对其具体发行版本做实机审计，因此不声称掌握原版最新作物数量、科技数量或完整机制。下面的数值是 FARM100 的设计目标，不是对原版数据的陈述。

正式对标前，固定原版版本、日期、画质和代表性存档，保存可复核的实机录像及机制清单。若暂时无法取得参考证据，可以推进本项目自身的交付，但“与原版同等级”的结论保持待验证。

| 维度 | 当前 0.1.0 | 目标体验 |
| --- | --- | --- |
| 农场生命感 | 成熟数值网格、单无人机位置插值 | 翻土、播种、成长、成熟、枯损、收获、补种持续发生 |
| 动作表现 | 格子高亮、数值直接变化 | 有起止和反馈的动作动画、声音、交换位移与连片收获 |
| 经营深度 | 单局排序后结束 | 生产、消耗、解锁、扩地、维护和优化构成长期循环 |
| 算法深度 | 相邻交换与路径成本 | 空间布局、时间安排、资源规划、探索、协作调度 |
| 多任务 | 单无人机、单关卡 | 多区域生产链、多个任务竞争资源、最多 8 台无人机协作 |
| 观看方式 | 编辑器与农场并排 | 可切换全屏观赏、跟随镜头、重点事件与双解法对比 |
| 可靠性 | 确定性执行和事件回放已建立 | 扩展后仍可复现，并补齐崩溃恢复与持久化历史 |

保留现有 Electron / React / PixiJS / QuickJS 基础。视觉先沿用二维俯视方向，增加有体积感的作物、光影与场景层次；不以更换成 3D 引擎作为达到观赏性的前提。采用原创美术、文案、音效和界面，具体规则根据本项目需要设计。

## 3. 观赏性目标

### 一眼能看懂，一分钟有变化，五分钟有过程

- 不看代码也能区分作物类别、成长阶段、成熟状态和无人机当前工作。
- 同屏具有近景围栏与工具、主体农田、外围环境等层次；装饰不能遮挡作物、路径与交互目标。
- 常规种植作物至少有播种、幼苗、生长、成熟四种可辨状态；特殊作物另有对应状态。数字作为可切换的测评叠层，不承担全部视觉表达。
- 无人机具有可辨朝向、移动、作业、等待与受阻反馈。交换必须看得到两株植物实际换位；收获具有局部或连片的完整过程。
- 动作音效、农场环境音、收获反馈支持独立音量和静音；倍速下限制重复音效密度。事件声音须与动作一致。
- 提供缩放、平移、无人机跟随、区域观察和全屏观赏。默认镜头稳定，自动切镜可关闭。
- 同一真实运行能够展示“准备田地 → 生长与维护 → 产出 → 重新投入生产”的完整变化。纯视觉待机效果不能伪装成算法动作。
- 支持输出一段连续 5 分钟、1080p 的真实运行演示；首期可使用外部录屏，后期提供内置导出。不能依靠剪辑隐藏停滞或错误。

验收素材覆盖：小田单机作业、大田混合作物、连片收获、多机生产、失败恢复。至少一段同时呈现两种策略在相同输入下的行为差异。

## 4. 系统复杂度目标

### A. 持续经营循环

实现土壤处理、播种、生长、浇水或其他维护、收获、仓储和再投入。资源有明确来源和用途，库存不能只是统计面板上的装饰数字。

设计至少 3 条相互关联的生产链，每条至少包含 3 个有实际决策作用的环节。例如基础作物产出支持土壤改良，改良提高特殊作物种植能力，特殊产出支持扩地或无人机能力升级。最终配方必须通过数值验证，不能出现新档无法恢复的资源死锁。

### B. 不同作物要求不同算法

以至少 8 类具有不同规则的可种植对象为内容目标，不能用换色计数。机制池覆盖：基础轮种、邻接或间距约束、水分与成长安排、区域融合、数值排序、成熟顺序选择、共生搭配、需要修复的损坏或障碍。

这些机制必须改变代码中的观察、判断或调度。每类至少提供一个能证明朴素策略与针对性策略行为不同的案例。

### C. 编程挑战形成梯度

至少形成 5 个挑战家族：自动耕作、空间布局、时间与资源调度、排序与连片收获、迷宫探索与寻路。多无人机作为横向系统贯穿其中，不只做成一次性的演示关。

每个家族至少 3 个递进任务，分别引入新约束、组合约束和开放优化。综合任务至少同时激活 3 种机制，使玩家必须取舍，而非按顺序调用几种 API 就结束。

### D. 成长与解锁改变策略

科技与任务图暂定至少 20 个有效节点，包含作物、土地、观察能力、自动化和协作能力，至少 3 个有资源取舍的分支。只有新增决策或能力的节点计入内容数量，纯数值加成不承担主要进度。

提供至少 12 个有反馈的引导任务，教会坐标、循环、条件、函数、状态记忆、路径与调度。新档能从零开始，不需要先粘贴最终通关脚本。已有 JavaScript 编辑器继续使用；Python 支持不作为本轮达成目标的必要条件。

### E. 多无人机是可编程系统

支持 1 / 2 / 4 / 8 台无人机的分阶段解锁。需要任务分配、局部状态、共享库存、通信或共享数据的明确语义，并定义同格移动、同时收获与资源争用的处理规则。

同输入、同代码、同版本必须产生相同结果。并行调度使用明确的模拟时钟、动作持续时间和稳定冲突顺序；不能由 Electron 消息到达先后决定胜负。程序并发接口在实现前单独设计并验证，不直接复制多个单机循环冒充协作。

## 5. 游戏深度与测评可信性共同成立

- 自由农场保存长期世界、资源、研究和脚本；挑战模式固定初始世界、能力、种子与约束。两种模式共用模拟规则，挑战模式不能偷偷继承自由农场的升级。
- 旧排序规则保留版本，新生长和并发规则使用新版本。旧 `.farmrun` 仍能按旧规则验证回放，不能因增加时间系统而改写旧成绩。
- 生长以模拟时间推进。暂停观看、跳转或调整播放倍率不改变引擎时钟、资源产出与结果。
- 新挑战按目标分别报告通关率、逻辑完成时间、操作成本、资源消耗及产出；每个挑战固定主指标及并列规则。多机效率不得仅看单台动作数，也不混成未经验证的总分。
- 每个家族具备朴素基线、针对性改进解、失败案例及固定测试集；不能据单个种子宣称算法全面更优。
- 日志覆盖田地生长、库存、研究、调度与动作。快照和回放要恢复完整世界，而不仅是画面位置。
- 补齐进行中事件持久化、崩溃后前缀恢复、历史检索和版本兼容；新规模需要流式记录与索引，不能只移除当前事件数量上限。

## 6. 实施里程碑与完成门槛

各阶段都交付可运行程序、示例存档或运行包、实际演示及验证记录。下表的先后顺序为实施依赖，不是工期承诺。

| 阶段 | 核心交付 | 完成门槛 |
| --- | --- | --- |
| G0 对标与扩展设计 | 原版参考证据、差距清单、视觉样板、世界与时钟协议 | 对标维度固定；旧规则兼容方案明确；缺失参考证据显式标为待验 |
| G1 可观赏的生产循环 | 原创农场美术、2 类作物、完整种收循环、动作与音效、观赏视图 | 真代码连续运行 5 分钟，至少完成 3 个生产周期；保存重开一致；种收动作清晰 |
| G2 可持续发展的农场 | 库存、3 条生产链、扩地、解锁图、引导任务、持续存档 | 从新档走通资源和解锁闭环；资源不足可诊断恢复；策略选择会影响后续发展 |
| G3 多机制编程挑战 | 达到 8 类作物与 5 个挑战家族的目标覆盖 | 每个家族具备递进任务、有效基线对比和可回放失败；组合任务证实系统相互作用 |
| G4 多机协作与测评 | 2/4/8 机、资源争用、协作接口、综合调度挑战 | 重复运行确定性一致；至少 2 个案例体现分工收益，至少 1 个体现协调开销 |
| G5 整体打磨与对标验收 | 全程成长体验、镜头音效完善、历史与恢复、性能优化、Windows 发行包 | 通过下面所有验收门槛；保留已知缺口；有实机参考才能给出对标结论 |

首个实施目标是 G0 → G1：先让真实代码驱动的农场拥有完整、可观看的生命循环，再扩展生产链和内容规模。G0 缺少原版实机证据不阻断独立设计，但不能绕过最终对标。

## 7. 最终验收方法

### 观赏性验收

使用固定参考条件，分别展示原版与 FARM100 的小田作业、混合生产和多机协作实录；保持相同展示分辨率、录像长度和可比的工作负载，记录实际场景差异。隐藏作品名称、交换播放顺序，降低品牌和顺序影响。

邀请至少 5 名未参与开发的体验者，其中至少 2 名不熟悉本项目代码，评估动作可读性、场景层次、变化丰富度、反馈完成度与持续观看意愿。每项采用预先写明锚点的 1～5 分制；FARM100 各项中位数目标至少 4 分，与参考的差距不超过 0.5 分。此为小样本产品验收依据，不冒充统计上证明等价。

同时，至少 4 人能在观看后准确描述当前作业、一次失败原因及两种策略的可见差异。数字标签或解说不能替代动作本身的清楚表达。没有参考实录时，仅能宣布内部视觉门槛通过。

### 系统深度验收

建立参考机制到本项目机制的映射表，按生产闭环、资源取舍、空间关系、时间约束、探索、协作、长期成长分别评价覆盖和深度。无需相同作物名字或相同配方，但每个参考核心维度都应有实际可玩的对应机制及程序案例。

上述内容数量达标只是最低覆盖检查。还必须提供至少 3 个综合案例：调整一种策略后，另一个生产或调度环节随之改变，并能从事件及指标中解释原因。录制从新档到多机综合任务的连续流程，确认所有能力都能实际解锁和使用。

### 工程与交付验收

- 固定测试集覆盖每个挑战家族至少 20 个种子；每个挑战至少有一个基线能通过其全部发布用案例。失败、资源边界和冲突另有专项案例。
- 小、中、大代表配置同输入各重复 10 次，逻辑结果一致；每个代表运行抽查至少 100 个回放跳转位置，与顺序恢复一致。
- 目标负载为 32×32 农场、8 台无人机和混合作物持续运行 30 分钟。冻结并记录验收机器的 CPU/GPU/内存、软件版本与渲染分辨率；1080p 下帧时间 p95 目标不超过 20 ms，30 分钟后内存无持续失控增长。未记录硬件与实测数据不得宣称达标。
- 1280×720、1920×1080 与 150%/200% DPI 的关键界面可用；高速回放允许压缩表现，但不能丢失逻辑事件或伪造动作轨迹。
- 在无开发环境的 Windows 实机或干净 VM 中验收离线安装、新档运行、存档重开、历史回放、对比、导出、升级兼容和卸载。

只有观赏性、系统深度、规则与回放正确性、发布可用性四项同时通过，才能将本目标标记为达成。当前 0.1.0 只是这一目标的基础，不给出缺乏证据的完成百分比。
